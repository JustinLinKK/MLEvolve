# Qwen3.8-27B INT8 on one L40S with vLLM

## Settings

- Hardware: one NVIDIA L40S (46,068 MiB), SM89.
- Model: `Qwen3.8-27B-INT8-W8A16-MTP`, text-only.
- Runtime: vLLM 0.28.0; compressed-tensors W8A16 with Marlin linear kernels, FlashAttention 2, FlashInfer sampling, Qwen GDN Triton/FLA prefill and CUDA decode.
- Server: one GPU, tensor parallelism 1, pipeline parallelism 1, `max_model_len=8192`, `gpu_memory_utilization=0.85`.
- Measurement: one excluded warm-up; then three streaming requests with `max_tokens=64`; first content delta is time to first token (TTFT).  Four simultaneous non-streaming requests measure aggregate throughput.

## Results

| Metric | Result |
| --- | ---: |
| Mean TTFT (3 trials) | 132.1 ms |
| Mean decode throughput | 21.58 tokens/s |
| Mean end-to-end throughput | 20.97 tokens/s |
| Four-request aggregate throughput | 42.43 tokens/s |
| Four-request wall time | 6.03 s |

The single-request target of about 10 tokens/s is exceeded by 2.16x. The benchmark payload and each trial are preserved in `l40s_vllm_eager_benchmark.json`.

## Compatibility result

The fastest default vLLM graph-compilation path cannot run with the node's system PyTorch 2.12 nightly: vLLM 0.28 calls `torch.fx.split_module(..., tuple_return=...)`, an interface present in its required PyTorch 2.13. Replacing system PyTorch/CUDA was intentionally avoided. The final healthy service therefore uses `--enforce-eager`; it retains the INT8/Marlin, FlashAttention 2, FlashInfer, and Qwen GDN kernels responsible for the measured throughput.

## Final service state

The service is healthy on `127.0.0.1:8000` inside the L40S pod, model name `qwen3.8-27b-int8-l40s`. No visual-model input is enabled.
